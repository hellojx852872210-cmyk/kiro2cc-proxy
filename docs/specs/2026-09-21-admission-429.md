# kiro2cc Admission / 429 Hardening Spec

状态：2026-09-21 用户授权的增量实施；仅代码/本地测试可交给Grok，镜像发布由主会话持锁完成。

## 1. 目标与基线

在现有 kiro2cc-proxy 3.3.5 / c7fa179 基础上，保留已部署的模型别名及cache-split补丁，只修复准入超发、流许可提前释放、限流信息丢失和刷新限流误禁账号。目标是减少无效上游尝试和错误禁号，不承诺扩张上游额度或未经压测的吞吐增益。

已证实根因：provider.rs 在200响应头返回后释放50/20 semaphore；RPM检查与成功后记账分离；上游Retry-After被丢弃，handler固定5秒；刷新429进入普通刷新失败计数。普通OpenAI错误转换同样不保留Retry-After。

## 2. 必须保留的行为

- priority/balanced既有策略，balanced为候选子集内原子轮询；不换成累计成功次数排序。
- 账号/端点429避让、正常会话sticky及ID派生、工具调用、普通Chat/Responses和/cc增量流，不引入整段缓冲。
- 全作用域月额度耗尽402，认证401/403处理，refresh invalid_grant禁用机制。
- fable-5.1别名、cacheCreationSplitRatio及其Admin/API/UI与现有usage计价逻辑不变。
- 不改变生产账号、单号RPM数值、计价、模型、入口端口、卷、权限；不改inject/sub2api/邻居容器。
- 不升级依赖，不引入新crate；可用chrono解析HTTP-date，现有http/reqwest/thiserror/futures/tokio足够。
- 不把HTTP200响应头当流完整结束；本轮不顺手重构所有成功指标。

## 3. 原子账号RPM

RpmTracker新增原子check-and-reserve接口，在同一锁内检查/预留账号一分钟预算，返回可发送或剩余等待时间。0继续表示关闭限制。

- 一次真正发出的模型API或MCP尝试必须消耗一次预算，包括上游429/5xx/网络失败；成功时不再重复记账。
- 在构造/校验请求和取得并发许可之后、网络send之前预留；若没有发送（预算满、没有端点、队列满），不扣尝试预算。
- 多线程同时申请额度8，最多8个成功预留；其他必须转候选或返回类型化本地限流，禁止单号池绕过限额。
- RPM满的等待不持有账号或全局活跃流许可。不在请求里睡到60秒；遍历有效候选后返回429及最早候选恢复时间（向上取整，至少1秒）。
- 修正无continuation_id时的避让丢失，至少保证本次因RPM/并发满被排除的候选不会立即被fallback强行再用。不得绕过bound_ids和模型资格。
- 现有RPM展示读数仍可用，明确账号维度现在统计尝试而非仅成功头。
- 使用精确滑动窗口或保守窗口；不接受由于整秒桶提前过期导致任意60秒窗口超额。可给每号独立Instant队列做准入，保持原展示计数。

## 4. 完整响应生命周期的许可

增加最小有类型的响应封装（例如 kiro::response::LeasedResponse），包含reqwest::Response、全局及账号OwnedSemaphorePermit，调用者不应轻易剥离guard。

- API、MCP返回值统一携带许可；非流读取text/bytes期间保留，流bytes_stream直到EOF/传输错误/丢弃/客户端取消都持有并最终释放。
- 收到200响应头不释放。包装流读到EOF/Err后立即释放，不依赖额外一次poll；Drop也必须释放。
- 错误重试在sleep之前归还两个活跃许可；token刷新、RPM等待、寻找账号不能持有活跃流槽。
- 多轮WebSearch必须在新一轮申请前释放已结束上一轮的许可，避免global=1自锁。临时dummy Response测试需通过显式test helper包装，禁止生产无guard逃逸。
- 全局/账号默认上限仍50/20。新增配置只为明确边界与测试：maxConcurrentRequests=50、maxConcurrentPerCredential=20、admissionTimeoutMs=5000、maxAdmissionWaiters=100；必须校验非零及合理上界，旧配置反序列化兼容。
- 已满账号应尝试其他合格账号；不要在一个满账号上占住全局槽。队列数量和等待时间有界，超时/满队列返回类型化local busy 429 + Retry-After，不能无限积压。客户端取消不会泄漏waiter槽。
- 准入票从provider入口、token获取之前非阻塞获取，覆盖整个建连/重试准备阶段，成功返回LeasedResponse时归还；最多maxAdmissionWaiters个未交付响应的provider调用，取消/错误释放。活跃流另受50/20限制。
- admission deadline从provider入口开始，换账号/重试不重置；约束客户对token准备/锁等待/许可等待的等待，已发送的推理请求与读body仍用原1000s超时。若重试准备时deadline已过，优先返回最后typed429或原始上游错误，不把它覆盖成local busy。
- **审计修订：不能直接timeout/drop已发出的OAuth刷新future**，因为上游可能已轮换refreshToken。token准备由独立有界任务运行完整acquire→刷新→内存更新→持久化；数量上限复用maxAdmissionWaiters，槽由任务持有到结束，避免无限detach。请求超时/取消只停止等待；任务不得继续推理/MCP。复用既有refresh_lock重检，不扩大为新的调度框架；模型/MCP任务仍须随客户取消abort。
- 双活跃许可用try-acquire组合；一个拿不到即释放另一个，再尝试其他合格候选或短暂等待，不能持一个等待另一个。RPM成功预留后直到调用send之间不得再await。
- 默认50/20、5000ms、100；并发及waiter允许1..=10000、timeout允许1..=60000。global=1/account20合法，实际受较小者约束；缺省兼容，显式0/越界配置启动报清晰错误，不扩大Admin/UI。
- 多轮搜索的后台JoinHandle必须abort-on-drop，客户端取消后不得detach继续发MCP或续轮。global=1下MCP在途断开要释放其许可，不能继续打下一轮模型。
- 不要求本轮实现least-inflight，避免把修复扩大为新调度系统。

## 5. 类型化限流与响应头

新增 kiro::error 的 RateLimitError（可区分upstream/RPM/local_busy/refresh），保存安全的retry_after头及内部等待截止时间/来源，不携带凭据或上游正文给客户。

- HTTP429收到响应时，在消费body前读取Retry-After。支持整数秒和IMF-fixdate；非法/负数/溢出丢弃，采用既有安全退避/本地最小值，不反射垃圾头。
- 有效上游Retry-After：立即结束当前provider调用并向客户返回429，不在本次调用换桶/换号绕过；新请求可使用其他合格桶/账号。模型冷却键为(账号,模型API端点)，MCP单独按账号的MCP桶，refresh另按账号；并发更新取已有/新截止时间max，短429不能缩短长冷却。不存在有效头时保留现有模型端点30秒避让和账号轮转，仍有既有总尝试上限9。
- 保持真实等待值；本地排队/RPM输出计算得到的等待值，不固定全部为5秒。
- 后续候选选择失败、所有端点暂不可用不能覆盖已知429为502；全池月额度耗尽402优先保留。
- 普通Messages、/cc、Chat、Responses均传播合法Retry-After；OpenAI错误转换需保留此安全头，不透传所有内部headers。
- 纯WebSearch开流前的MCP429必须返回真实429，不得吞成空结果200。混合工具场景若已开流，不能改HTTP状态；明确error SSE后终止当前失败路径，不伪造成功文本，不吞错误继续额外模型轮次。
- 非流式混合搜索尚未发HTTP响应时，MCP/续轮typed429应返回429+安全头，不变成空结果并额外调用模型；已开流明确error并终止。对一般非429搜索降级行为不顺手扩面。
- 改动范围内传输读错误不可伪装成正常结束。保留既有SSE错误格式，不新增假签名、cache逻辑或模型字段。

## 6. 刷新限流不误禁账号

Social、IdC、external_idp刷新收到429，返回上述typed refresh限流。acquire_context/global/filtered/sticky、force_refresh及调用provider的路径均识别它：不增refresh_failure、不禁用、不清掉有效凭据。

- 每账号维护进程内refresh限流截止时间，等待者取得既有refresh_lock后需再检查，防止失败后的串行刷新风暴。
- 有效Retry-After用其时间；无头采用短暂默认冷却5秒。只影响当前账号，不把一个账号限流扩大到全部账号。
- 可换其他合格账号；没有其他账号时返回429及等待时间，不在每次请求里反复撞刷新接口。
- invalid_grant和非429永久错误保持原语义；不在本轮重构成每号刷新锁。

## 7. 可执行验收矩阵

A01 原子RPM：16并发竞争limit8恰好最多8准入；0关闭；窗口恢复；实际尝试失败仍消耗；成功不双记。
A02 许可：global2/account1，先拿200并持续输出时第三个流不能突破；EOF、Err、cancel立即释放；其他账号可前进。
A03 队列：waiter上限与5s等待期限生效；取消释放；等待期间没有占用活跃槽。
A04 重试：模型与MCP的429/5xx每尝试计数；退避无槽；上一流释放后global1多轮搜索可继续。
A05 Retry-After：37秒、未来HTTP-date、0、非法、负数、超大值；所有四入口状态/头一致；候选耗尽仍429而非502。
A06 刷新：各认证类型429保持账号未禁用/失败计数不变；同账号后续请求不重复刷新；另一账号可用；到期恢复；invalid_grant回归。
A07 保留能力：现有所有测试，fable别名、cache split、402、工具往返、普通Chat/Responses与/cc实时增量。
A08 原症状：通过真实provider+HTTP mock，上游先回200并hold流，再并发请求；通过真实provider+mock429，核对实际上游尝试数、返回头和下一次准入。
A09 不读生产凭据；测试只用假token和loopback/mock端点，不启动真实Kiro请求；公开测试配置不含真实账号/密钥。
A10 同桶长/短Retry-After乱序取max；模型/MCP/refresh桶互不误封；原有bound_ids与模型资格不被fallback绕过。
A11 token刷新阻塞时大量请求仍受准入票上限/同一个deadline约束；global1的MCP中客户端取消，不再发续轮、所有槽归还。
A12 非流混合搜索429在Messages/OpenAI仍保留HTTP429+头；旧JSON缺省值兼容，新字段零/超界启动拒绝，global1/account20合法。
A13 保留端点fallback：同号IDE返回429且无有效Retry-After、Runtime可200，同次请求应成功、两次真实发送；区分硬避让（RPM/并发/全桶冷却）与软换号偏好。有效Retry-After仍立即返回。
A14 延迟OAuth返回轮换token：客户及时429/取消且未发推理，后台完整保存新token，后续请求可用；并发超时不会突破独立准备任务上限，同账号不重复刷新。

尽量使用现有inline tests，必须有失败→通过证据。若用cfg(test)注入测试端点/小许可，仅测试构造可用，生产不得新增可任意重定向凭据的mock开关。镜像级验收另由主会话使用隔离网络/受信测试CA代理或test-stage做HTTP测试，再对release镜像做启动/鉴权/资源检查；mock不是付费真路径替代。

## 8. 实施与发布权限

Grok只在隔离本地工作树产补丁和测试，不commit/push、不SSH、不Docker生产、不读取家目录凭据。主会话review实际diff及测试，冻结commit和镜像摘要，在用户授权范围内执行发布。

发布前：服务器侧独占flock；比较当前容器image/config及源码基线（CAS），发生变化就停止而非覆盖；保留旧镜像，备份compose/config到受限目录，不能在回滚时覆盖发布后变化的usage/凭据。候选镜像先隔离测试，真实小预算冒烟另需用户明确credits预算。原路径未验收不得把mock结果当已修复上线。

只替换目标服务镜像；保留端口/网络/卷/环境/重启策略。短暂排空/中断风险需发布前告知。失败立即回旧镜像，不删除旧卷/镜像、不重启其他服务。GitHub只推fork的独立分支，不自动向上游发PR。
